# コーディングルール（一般）

このドキュメントは、Nikki プロジェクト全体に適用される一般的なコーディングルールを定義します。

（グローバル規約 `~/.claude/rules` と重複する項目は本ファイルに書きません。冪等性・Single Source of Truth・中間変数・memberwise initializer・定義のドキュメントコメントなどはグローバル規約を参照してください）

## 基本原則

- コーディング規約から逸脱したい場合はコメントに理由を書いてください
- **コードの読みやすさを優先する**
- **宣言的なスタイルを使用する**: 手続き的なコードよりも宣言的なコードを優先する
- **パフォーマンス最適化は基本的に考慮しない。コードの読みやすさを優先する**
  - N+1問題のようなパフォーマンス問題は、以下の場合を除いて考慮しない
  - パフォーマンス最適化を考慮する例外:
    - 100件を超える件数を扱う場合
    - bodyから表示のための計算で数十件のデータを使っていて、それを用いて都度計算されているようなパターン
  - それ以外のケースでは、バルク処理などの最適化よりも、コードの読みやすさを優先する

## インデントとフォーマット

- インデントは4スペースにする
  - Focus は tab(=2space) を採用しているが、Nikki の既存コードは4スペースで統一されているため、現状に合わせる（プロジェクトに `.swift-format` は未導入）
- 標準型の拡張ファイルは `{TypeName}+.swift` のような命名にする（例: `Date+.swift`, `String+.swift`）
  - 1つの型に対して1つの拡張ファイルを使用し、ファイル内で複数の拡張がある場合は `// MARK: -` を使って機能ごとにセクション分けする

## guard と if の使い分け

- **`guard` は関数の事前条件にのみ使用する**
  - 関数の引数チェック、必須パラメータの検証など、その関数が実行できる前提条件を確認する場合に使用
- **`if` はロジックに関わる条件すべてに使用する**
  - データの検証、フィルタリング、ビジネスロジックの分岐など、ロジックに関わる条件判定には `if` を使用
  - ループ内で `continue` や `break` を使う場合でも、ロジック条件であれば `if` を使用する（`guard ... else { continue }` は使わない）
- 理由: `guard` と `if` が入り混じると読みづらくなる。ロジックに関わる箇所は全て `if` で表現することで、コードの一貫性と可読性が向上する

### guard/if 文は1行で書かない

- `guard let ... else { return }` や `if let ... { ... }` を1行にまとめて書かない
- 条件部分、else句（guardの場合）、本体（ifの場合）はそれぞれ別の行に分ける

良い例:
```swift
guard let match, match.numberOfRanges > 1 else {
    return
}
```

悪い例:
```swift
guard let match, match.numberOfRanges > 1 else { return }
```

## コメントの書き方

### プロパティのコメントは横ではなく上に書く

enumのケースやプロパティの説明コメントは、同じ行ではなく上の行に記載する

良い例:
```swift
enum InkNavLeading {
    // 先頭ボタンなし
    case none
    // 戻るボタン
    case back
    // 閉じるボタン
    case dismiss
}
```

悪い例:
```swift
enum InkNavLeading {
    case none     // 先頭ボタンなし
    case back     // 戻るボタン
    case dismiss  // 閉じるボタン
}
```

### コメントには具体的な数値を書かない

- コードに書いてある具体的な数値はコードを見ればわかるので、コメントには書かない
- コメントには「何を調整しているか」「どのような意図か」を書く
- 良い例: `// 段落間ギャップを行内の行間より広くするための余白`
- 悪い例: `// 段落の上下に line-height 2.05 相当の余白（12pt）を足す` （数値がコードに書いてあるので不要）

## Calendar と Locale

- **Calendar と Locale は `.current` ではなく `.autoupdatingCurrent` を使用する**
  - `.current` はインスタンス作成時の設定を保持し続けるため、アプリ実行中にユーザーがシステム設定（タイムゾーン、言語、カレンダーなど）を変更しても反映されない
  - `.autoupdatingCurrent` はシステム設定の変更を自動的に反映するため、ユーザー体験が向上する
  - 例外: プレビュー・サンプルデータで再現性のために固定した Calendar を使う場合（例: `SampleData.calendar`）は、その旨をコメントで明記する

## 現在時刻

- 現在時刻が必要な場合は `Date()` ではなく `Date.now` を使用する
- `Date()` はイニシャライザ呼び出しで冗長であり、`Date.now` の方が意図が明確

## 状態とプロパティの宣言

- 状態の宣言は最小限に
  - 特定の値が存在する場合、特定の値がどのようになっているかを考えて重複した意味にならないかを十分に検討してください
  - 特に onChange(of:) を使用して状態を更新している場合は疑った方が良いです
- **記述が短くなる、という理由だけで変数やプロパティを宣言しない**
  - 変数・プロパティは意味のある抽象化や再利用のために宣言する
  - 単に記述を短くするだけの目的で宣言すると、かえって可読性が下がり、コードの意図が不明確になる
  - 1回しか使わない値を変数に入れるのは避ける。直接使用する方が明確
- **ただ関数を呼ぶだけの computed property（getter）を作らない**
  - 関数を1回呼ぶだけのラッパー getter は宣言せず、関数を直接呼び出す
  - 同じ値を複数回参照して二重計算を避けたい場合は、`body` 等の中でローカル `let` に束縛する（getter は作らない）

## Equatable と Hashable

- **Equatable と Hashable の実装は極力定義しない**
  - Swiftのコンパイラは Equatable と Hashable の実装を自動合成できる
  - `==` や `hash(into:)` を手動実装すると、プロパティ追加時に更新漏れが発生しやすく、バグの原因になる
  - 手動実装が必要な場合（パフォーマンス最適化、特定プロパティのみで比較など）は、コメントで理由を明記する
  - 良い例: プロトコル準拠の宣言のみ（`struct JournalEntry: Identifiable, Hashable`）→ コンパイラが自動合成
  - 悪い例: `static func ==` や `func hash(into:)` を不要に実装

## デフォルト引数

- **デフォルト引数は複数の使用パターンがある場合にのみ使用する**
- 1パターンしか使われないのにデフォルト引数を宣言しない。呼び出し側で直接値を渡す

## データの所有と計算ロジック

### データの所有者が計算責任を持つ

- あるデータから派生する計算ロジックは、そのデータを所有する型が責任を持つべき
- computed property を使って、派生データの計算ロジックを所有者に集約する
- 使用側で毎回同じ計算ロジックを書くのは DRY 原則に反する

良い例（`JournalEntry` が本文ブロックから抜粋テキストを計算する）:
```swift
struct JournalEntry: Identifiable, Hashable {
    var blocks: [Block]

    /// 一覧の抜粋に使う、本文段落を連結したプレーンテキスト。
    var excerpt: String {
        blocks.compactMap { block -> String? in
            switch block {
            case .paragraph(_, let text): return text
            case .heading(_, _, let text): return text
            default: return nil
            }
        }
        .joined(separator: " ")
    }
}
```

悪い例:
```swift
// 使用側で毎回計算
let excerpt = entry.blocks.compactMap { ... }.joined(separator: " ")
```

### ロジックの重複を無理に共通化しない

- 別の目的・別のユースケースで同じようなロジックが出てきても、無理に共通化しない
- それぞれ別のロジックとして書けば良い。無理な共通化はかえって保守性を下げる
- 本当に同じロジックを使っているのであれば共通化すべきだが、似ているだけのロジックは別々に書く

## @Observable の使用

- **`@Observable` は原則使用しない**。View 内の状態は `@State` + `@Binding` で表現する
- どうしても `@Observable` を使わなければいけない理由がある場合（アプリ全体で共有する状態オブジェクトなど）は、その理由をコメントに書くこと
